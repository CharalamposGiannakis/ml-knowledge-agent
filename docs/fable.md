# fable.md — Independent Reliability & Effectiveness Audit

> Auditor: external principal-engineer review (Claude Fable 5), 2026-07-03.
> Scope: read-only. Every claim below was checked against the repo at commit `e9ade94`;
> where a claim depends on runtime behavior, I ran the actual scripts and include the result.
> Fuseki was **down** during the audit, so live-graph checks (healthcheck.py) were exercised
> in their failure path only; file-level checks (SHACL gate, OWL consistency) ran for real.

---

## Executive summary

1. **The safety harness is weaker than its documentation.** I fed the SHACL gate a result pointing at a *nonexistent* dataset URI and a result whose "dataset" is `:XGBoost` — **both passed**. The Layer-3 OWL check then reported both **CONSISTENT**, and also passed one IRI carrying two different `:hasValue` literals. Of the harness's advertised catches (referential integrity, disjointness, functional-property contradictions), I could demonstrate none.
2. **Reliability is asserted by process, not by code.** Zero automated tests (a scorer bug already shipped undetected), no dependency manifest, no `temperature=0` or prompt-version pinning on the extraction call, and a value cross-checker that silently skips exactly the messy cells it exists to catch.
3. **The README sells a product that doesn't exist yet.** No agent, no review UI, no ChromaDB, no FastAPI, no conditions in the graph (0 `:Condition` nodes; every result `conditionsComplete false`), and an eval set of 2 pairs instead of the promised ~30. The README's flagship example query is unanswerable by the current graph *in principle*.
4. **Verdict: the architecture is sound and the discipline is real** — ADRs match code unusually well, the raw+canonical+SKOS design is genuinely good, and I independently corroborated 8/8 sampled beyond-gold values against the PDF. But the project's distinctive claim ("validated, no hallucination") currently rests on one human and one paper, not on the machinery — and the machinery's gaps are exactly where a skeptical interviewer will probe.
5. **Highest-leverage next move:** fix the gate (one parameter + type assertions), add a test suite, then build the query agent before ingesting paper #2. One paper + working agent + eval beats five papers + no agent, on all three project goals.

## Strengths (earned, not courtesy)

- **Decision hygiene is exceptional for a personal project.** ADR-001..015 are real decisions with rejected alternatives; `DESIGN.md`/`STATUS.md`/code agree with each other far more than is typical. A fresh reader can reconstruct *why* within an hour.
- **The core data-model call is right.** Result-as-atom (ADR-002) with query-time comparison is the correct shape for N-way tables, and raw-string + null-canonical + SKOS-alias resolution living *in the graph* (ADR-013) is the strongest single design in the repo — it makes entity identity auditable and self-improving.
- **Deterministic code owns the RDF.** Strict JSON from the model, TTL from code (`emit_ttl`), no auto-commit, human gate. The model never writes triples. This is the right trust boundary.
- **Fail-loud instincts.** `init_fuseki.sh` refuses to run without a password; extraction exits on `max_tokens` truncation and saves the raw response before parsing; the gold file is frozen and never regenerated by the pipeline (ADR-014).
- **The data itself checks out.** I extracted page-6 text from the PDF and searched for 8 beyond-gold values from `data/shwartzziv2022_full.ttl` (24.25, 10.95, 55.59, 78.99, 14.69, 20.18, 13.82, 77.98): all 8 appear verbatim on the page. I also suspected the `ds_mslr`→CrossEntropyLoss assignment was wrong; the actual Table 2 caption confirms the graph is right. The 88 records look trustworthy.
- **Deterministic IRIs (ADR-014) with idempotent loads** — correct instinct, correctly scoped (with one deferred hole; see H4).

## Findings

### CRITICAL

**C1. The SHACL gate's referential-integrity checks are vacuous.**
`scripts/validate_shapes.py:44` runs pyshacl with `inference="rdfs"`. The ontology declares `rdfs:range` on all core properties (`ontology/mlkg.ttl:57-64`), so RDFS closure *invents the type the shape then checks for*: any object of `:onDataset` is inferred `a :Dataset` before `sh:class :Dataset` runs. Demonstrated:

- A result pointing at `:ds_TYPO_DOES_NOT_EXIST` (no type, no label, defined nowhere) → **`SHACL PASS`**.
- A result with `:onDataset :XGBoost` (a Method; classes are pairwise disjoint) → **`SHACL PASS`**.
- A dangling *metric* fails, but only incidentally — `MetricShape` demands `:optimizationDirection` (`ontology/shapes.ttl:36-40`), not because `sh:class` worked.

`docs/health_checks.md:9` claims Layer 1 enforces "referential integrity (sh:class)". It does not. A typo'd dataset IRI sails through the gate, is invisible to Layer 2 (healthcheck B covers methods only, `scripts/healthcheck.py:32-38`) and Layer 3 (see C2), and produces silently incomplete query answers — the exact failure mode ADR-013 exists to prevent.
**Fix:** set `inference="none"` and require asserted types. Emitted/reviewed TTL already types its entities, and the gate merges the ontology (`validate_shapes.py:39`), so canonical individuals are covered — I verified the shapes still make sense against existing data files. Add a `DatasetShape`/method-shape requiring `rdfs:label` so dangling URIs fail for the right reason. Then keep the three bad-TTL probes from this audit as regression fixtures. *Effort: ~1 hour + tests.*

**C2. Layer 3 (OWL consistency) is a no-op in practice.**
`docs/health_checks.md:49` says it "catches disjoint-class violations, functional-property contradictions." Demonstrated on `scripts/consistency.py`:
- The cross-typed file (`:XGBoost` as both Method and Dataset under `owl:AllDisjointClasses`, `mlkg.ttl:48-50`) → **CONSISTENT**.
- One result IRI with `hasValue 1.11, 2.22` (`:hasValue` is `owl:FunctionalProperty`) → **CONSISTENT**.
Both advertised catch classes are empirically dead (owlrl either doesn't process `owl:AllDisjointClasses` membership into `owl:Nothing`, or does not surface literal clashes on functional datatype properties as `owl:Nothing`). The check provides negative assurance value: it prints "CONSISTENT" over broken states.
**Fix:** replace or supplement with SPARQL invariants that actually fire: `?x a :Method, :Dataset` (pairwise cross-typing), `?r :hasValue ?v1, ?v2 FILTER(?v1 != ?v2)`, and equivalents for the other functional properties. If keeping owlrl, first write a failing-case test proving it detects *something*; if it can't, delete it and update `health_checks.md` — an honest 2-layer harness beats a fictional 3-layer one. *Effort: half a day.*

**C3. Zero automated tests, and one bug already shipped to prove the point.**
There is no `tests/` directory, no CI, no dependency manifest (`requirements.txt`/`pyproject.toml` absent — pymupdf, anthropic, rdflib, pyshacl, owlrl all unpinned). STATUS.md:39 and :42 record two scorer bugs found by luck, not tests. Meanwhile latent defects sit in reviewed code: `_parse_cell` contains a no-op `text.replace("±", "±")` (`scripts/phase2_extract.py:279` — presumably meant to normalize some other character) and its regex rejects negative numbers, so any negative-valued table gets no cross-check at all.
**Fix:** pytest over the pure functions — `_parse_cell` (±, `+/-`, negatives, commas, scientific notation, footnote-contaminated cells), `_normalise_result` (each flag reason), `emit_ttl` (IRI determinism, collision), `_canon_local`, the scorer's matching logic — plus the C1/C2 fixtures run against the gate. Pin dependencies. *Effort: one focused day; the highest ROI in this list.*

### HIGH

**H1. The value cross-check silently skips exactly the cells most likely to be wrong.**
`phase2_extract.py:354-356`: the `value_parse_mismatch` flag fires only when `_parse_cell` *succeeds* and disagrees. If the cell fails to parse (footnote marker, bold marker, unicode minus, `%`, brace annotation — i.e., every messy table this pipeline will ever meet beyond this one clean paper), the check is skipped and the LLM's `value` is trusted blind. The safety mechanism is inversely correlated with risk.
**Fix:** unparseable `raw_cell` ⇒ raise a `value_unverifiable` flag (`requires_human_answer: true`). Extend the regex for negatives and `%`. *Effort: ~1 hour.*

**H2. Extraction is not reproducible and not versioned.**
`phase2_extract.py:227-244`: no `temperature` (Anthropic default is 1.0 — needlessly stochastic for closed IE), no prompt version recorded anywhere, `extracted_by` is a string the *model copies from the schema template* (`:69`) rather than derived from `MODEL` — if you switch models, provenance silently lies. The raw response is saved (good) but to a fixed path overwritten on every re-run (`:251-253`), so the audit trail of run N-1 dies at run N. ADR-014 makes IRIs deterministic; nothing makes the *content* deterministic or traceable.
**Fix:** `temperature=0`; add a `PROMPT_VERSION` constant written into the JSONL header and TTL comment block; derive `extracted_by` from `MODEL` + prompt version; timestamp raw-output filenames. *Effort: ~1 hour.*

**H3. There is no accuracy story for paper #2.**
The measured "100% P/R" exists because paper #1 has hand-made gold (ADR-010). For every future paper the plan is: flags catch identity issues, a human eyeballs the rest. Two problems:
(a) *The scorer cannot measure identity precision even where gold exists.* `eval_extraction.py:199-205` scores method/dataset/metric as "correct by construction of the key match" — a record whose method was mis-canonicalised produces a wrong key, lands in "beyond gold," and is **excluded from the precision denominator** (`:193-195`). Mis-identification is systematically invisible to the headline number. The STATUS.md claim "100% P/R all fields" is partly tautological.
(b) *Nothing supports or records the human verification of non-flagged records.* ADR-004 promises a persisted accept/edit/reject log ("free labeled dataset"); no such log exists anywhere in the repo. Phase-2 flag resolutions live only in chat history and STATUS prose.
**Fix:** per-paper review protocol: verify all flagged + a random sample of N clean records against the rendered page, and persist every decision to `proposals/<paper>_decisions.jsonl`. That file is the seed of the Phase-3 UI and the only honest basis for "measured reliability" beyond paper #1. *Effort: protocol is free; decision-log plumbing ~half a day.*

**H4. Cross-load integrity is unguarded, and the IRI scheme has a known collision window.**
The gate validates `file + ontology` in isolation (`validate_shapes.py:39-40`) — never the union with the live graph. Combined with ADR-014's deferred condition-hash, the trap is concrete: the *next planned task* (modeling seen/unseen for Shwartz-Ziv) creates two results per (method, dataset, metric) that mint the **same IRI**, and a second load merges them into one node with two `hasValue`s. Demonstrated: that merged state passes the gate when split across loads, passes healthcheck C (same IRI ⇒ `STR(?a) < STR(?b)` never true, `healthcheck.py:41-48`), and passes Layer 3 (C2). All three layers blind, on the roadmap's very next step.
**Fix (ordered):** (1) healthcheck E: `?r :hasValue ?v1, ?v2 FILTER(?v1 != ?v2)`; (2) emit-time duplicate-key detection in `emit_ttl` (a dict keyed on the IRI; collision ⇒ flag, don't emit); (3) do the `__{cond_hash}` IRI migration *now*, while exactly one paper would need regenerating — it gets strictly more expensive every paper. *Effort: (1)+(2) ~2 hours; (3) ~half a day.*

**H5. The conditions machinery is ontology-ware, not software.**
Reified `:Condition`, numeric/text value split, controlled `:ConditionType` vocabulary, min/max ranges (`mlkg.ttl:106-116`) — none of it has ever held data: **0 Condition nodes** across all data and proposal files; `conditionsComplete false` on all 88 results; the extraction prompt hard-codes `conditions: []` (`phase2_extract.py:222`). Meanwhile the ingested paper's *central experimental variable* (seen/unseen datasets) is exactly a condition, so today's graph blurs the one distinction its own source paper is about, and every honest answer requires a caveat that no component exists to deliver. The README's showcase query (rows≈5,000, noisy labels) filters on conditions — unanswerable in principle.
**Fix:** model seen/unseen for Shwartz-Ziv (already STATUS next-action #2 — raise it above adding paper #2), coupled with the H4 IRI migration since conditions enter result identity together. *Effort: ~1 day including regeneration and reload.*

### MEDIUM

**M1. README describes the destination in the present tense.**
"The agent translates it into a structured query… responds with…" (`README.md:19-27`), semantic layer/ChromaDB (`:79`), FastAPI agent (`:81`), chat UI (`:83`) — none exist. The eval set holds 2 pairs (`eval/eval_set.jsonl`), not the ~30 of ADR-006, and has no runner (Layer 4 is a file, not a check). As a portfolio piece this is the most dangerous gap: the repo's pitch invites exactly the questions its code can't survive. **Fix:** a "Status today vs roadmap" block in the README; grow the eval set as the agent lands. *Effort: 30 minutes of honesty.*

**M2. The stored ×100 scale factor breaks cross-paper comparison — the system's core premise.**
Values are stored as printed (STATUS known-issue), which cancels within one table. But comparison-at-query-time is the whole point (ADR-002), and the moment paper #2 reports unscaled cross-entropy on `ds_covertype`, SPARQL will happily compare 3.13 (×100) against 0.031 (×1) with no signal that they're incommensurable. The scale lives only in a caption string and an `rdfs:comment`. **Fix:** a `:valueScale` datatype property on BenchmarkResult (default 1), set at review, consulted by the future agent; or normalize to canonical scale at review and record the printed form in `:sourceText`. Decide *before* paper #2, then it's an ADR; after, it's a migration. *Effort: small now.*

**M3. Per-paper metadata is hard-coded in the extractor.**
`PAPER_META` dict in source (`phase2_extract.py:44-49`); unknown paper falls back to `:paper_unknown`, unknown locator to a single `:src_{paper}_proposed` IRI (`:423`) — so two different unregistered tables of one paper collide on one SourceLocation across runs (same cross-load blindness as H4). **Fix:** mint `src` IRIs from `paper_id + locator` slug; move paper metadata to a small TTL/JSON the script reads; fail loudly on unknown paper instead of `:paper_unknown`. *Effort: ~2 hours.*

**M4. Infrastructure hygiene.**
`docker-compose.yml:7` uses `stain/jena-fuseki:latest` — an unpinned tag of a community image that has been dormant for years (Jena 3.x era; the compose file's own comment says Jena is on 5.x and to verify). Password falls back to `admin` in both compose (`:13`) and `load_data.sh:10`. **Fix:** pin a maintained image (official `jena-fuseki-docker` or `secoresearch/fuseki` at a specific version); remove the `admin` fallbacks (fail like `init_fuseki.sh` does). *Effort: ~1 hour + one migration of the volume.*

**M5. Secrets handling has two soft spots.**
(a) The real Fuseki admin password is embedded in a permission rule in `.claude/settings.local.json` — protected today only by the *user-global* git ignore, not the repo's `.gitignore`; on any other machine/clone that file pattern is one habit away from being committed. (b) `CLAUDE.md:46` says `cp .env.example .env` but the tracked template is `env.example` (no dot) — the documented setup command fails. **Fix:** add `.claude/` to the repo `.gitignore`, rotate the password, rename the template or the doc. *Effort: minutes.*

**M6. 1 → 100 papers: the honest scaling ledger.**
- *Human review:* ~45 min/paper is the stated philosophy ⇒ ~75 hours per 100 papers. Consistent with the design, but say it out loud: this is a dozens-of-papers system by construction. Fine — if stated.
- *Extraction mechanics:* one table per manual invocation with hand-supplied `--page`/`--locator`; `max_tokens=16384` with "edit the constant and re-run" as the overflow remedy (`phase2_extract.py:256-260`); no retry/backoff on the API call. Multi-table papers mean N invocations and N chances for locator typos (which the gate, per C1, won't catch).
- *Vocabulary prompt* grows linearly with entities — fine to ~100 papers, but casefold collisions resolve silently first-wins (`phase2_extract.py:155`); make collisions loud.
- *Dedup:* dataset recurrence across papers is parked (STATUS parking lot) and arrives with paper #2, not paper #20. ADR-013's alias flow handles the *name*; nothing yet decides variant-vs-same (split, preprocessing).
- *Hardcoded regressions:* healthcheck D pins one flagship value in code; per-paper invariants need to come from data (e.g., generated from each paper's decisions log), not from editing `healthcheck.py`.
- *Query performance:* a non-issue; TDB2 at this schema is comfortable far past 100 papers (~1M triples). Fuseki is not your bottleneck; you are.

### LOW

**L1.** `healthcheck.py` conflates "graph is wrong" with "server is down" — all four checks FAIL with connection stack traces when Fuseki is stopped (observed live). Ping first; report "UNREACHABLE" distinctly. *~15 min.*
**L2.** `_METRIC_SCALE_RE` handles only ×100 (`phase2_extract.py:60-62`); ×10, ×1000, `%` variants will appear. Generalize when M2 is decided.
**L3.** Windows friction: scripts assume `python3`/bash; repo runs on win32 via Git Bash. Works, but document it or add a `py -3` shim note.
**L4.** `data/shwartzziv2022.ttl` (gold, `:r_xgboost_*` IRIs) and `_full.ttl` (`:r_shwartzziv2022__*`) both pass the gate; loading both by mistake creates 48 healthcheck-C duplicates. The gold file's header should say "NEVER load; eval only" the way ADR-014 does.
**L5.** `.gitignore` lacks `.venv` variants it has, but also lacks `.claude/` (see M5) and `scripts/__pycache__` is present on disk (ignored, fine).

## Where I'd challenge the current design

**1. RDF/SPARQL is justified — but only by two of your three goals.** For "a tool I actually use," a single SQLite table with a `results` view would have delivered every query in this repo in a weekend, including provenance. The semantic stack earns its keep through the learning goal and the portfolio goal, and ADR-001 admits this. My challenge is narrower: the *complexity budget you accepted is being spent on the wrong layer*. You have SHACL, OWL disjointness axioms, SKOS, a reified condition model, and transient reasoning — and no agent, no UI, and no conditions data. The semantic-web stack is deepest exactly where no user-visible value flows through it yet. Rebalance: freeze ontology sophistication, spend the next chunk of budget on Phase 3/4.

**2. BenchmarkResult-as-atom is right; its *identity* is wrong (temporarily, by admission).** ADR-014 defers conditions from the IRI key. That means today's atom is really (paper, method, dataset, metric) — and the deferral's failure mode is not hypothetical, it's your next STATUS action item (H4). A deferred migration whose trigger is already scheduled isn't a deferral; it's a bug with a due date. Do it while the graph is 88 records.

**3. "Active review" is a philosophy with no artifact.** ADR-004 and ADR-012 are the project's best thinking, and their concrete deliverables — the decision log, the two-queue review, the one-keypress approval — exist nowhere. What actually happened for paper #1 was expert manual curation in chat, which is fine and produced good data, but it is *not the system the ADRs describe*, and it leaves no measurement trail. Until the decision log exists, "review is a built feature, not a chore" is aspiration, and the claimed labeled-dataset dividend is zero.

**4. The reliability pitch is currently circular for everything past paper #1.** Gold exists because a human entered the data; extraction is measured against it; future papers get no gold, so their accuracy claim reduces to "the same human checked it." That's honest curation — but the README/DESIGN language ("measured, not asserted") implies an ongoing measurement the protocol can't produce. The fix is cheap (H3's sampled-verification + persisted decisions gives you a running per-paper verified-sample rate) but the framing should change either way: you are building a *curated* graph with measured *assistance*, not a measured extraction system.

**5. The health harness proves the opposite of its intent right now.** A three-layer validation story that passes dangling references, cross-typed entities, and functional-property violations is worse for the portfolio than no story, because it's checkable — I checked it in under an hour with three small TTL files. Fix C1/C2 and keep my probe files as fixtures; then the harness becomes a genuine differentiator ("here are the adversarial cases my gate rejects, in CI").

**6. Is the whole approach solving the wrong problem? No — with one caveat.** The premise (structured, provenance-first benchmark facts beat RAG-over-chunks for this question class) is sound and the ingestion philosophy is coherent. The caveat: the system's value theorem is only provable at the query layer, and the query layer doesn't exist. Every week spent hardening extraction for hypothetical paper #50 before a single natural-language question can be answered end-to-end is a week spent on the empty-cathedral branch of your own ADR-007 warning.
